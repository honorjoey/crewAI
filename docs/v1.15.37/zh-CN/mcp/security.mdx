## 概述

<Warning>
MCP 安全最关键的方面是**信任**。您应该**仅**将您的 CrewAI 代理连接到您完全信任的 MCP 服务器。
</Warning>

将 MCP（模型上下文协议）服务器等外部服务集成到 CrewAI 代理中时，安全性至关重要。
MCP 服务器可以根据其公开的工具执行代码、访问数据或与其他系统交互。
了解其影响并遵循最佳实践来保护您的应用程序和数据至关重要。

### 风险

- 在运行代理的计算机上执行任意代码（尤其是使用 `Stdio` 传输，如果服务器可以控制执行的命令）。
- 暴露来自代理或其环境的敏感数据。
- 以意想不到的方式操纵代理的行为，包括代表您进行未经授权的 API 调用。
- 通过复杂的提示注入技术劫持代理的推理过程（见下文）。

### 1. 信任 MCP 服务器

<Warning>
**仅连接到您信任的 MCP 服务器。**
</Warning>

在配置 `MCPServerAdapter` 以连接到 MCP 服务器之前，请确保您了解：
- **谁操作服务器？** 它是已知的、信誉良好的服务，还是您控制下的内部服务器？
- **它公开了哪些工具？** 了解这些工具的功能。如果攻击者获得控制权或者服务器本身是恶意的，它们是否会被滥用？
- **它访问或处理哪些数据？** 了解可能发送到 MCP 服务器或由 MCP 服务器处理的任何敏感信息。

避免连接到未知或未经验证的 MCP 服务器，尤其是当您的代理处理敏感任务或数据时。

### 2. 通过工具元数据进行安全快速注入：“模型控制协议”风险

一个重大而微妙的风险是通过工具元数据进行提示注入的可能性。它的工作原理如下：

1.  当您的 CrewAI 代理连接到 MCP 服务器时，它通常会请求可用工具的列表。
2.  MCP 服务器响应每个工具的元数据，包括其名称、描述和参数描述。
3.  您的代理的底层语言模型 (LLM) 使用此元数据来了解如何以及何时使用这些工具。此元数据通常会合并到LLM的系统提示或上下文中。
4.  恶意 MCP 服务器可以制作其工具元数据（名称、描述）以包含隐藏或公开的指令。这些指令可以充当提示注入，有效地告诉您的 LLM 以某种方式行事、泄露敏感信息或执行恶意操作。

**至关重要的是，这种攻击只需连接到恶意服务器并列出其工具即可发生，即使您的代理从未明确决定“使用”任何这些工具。**仅仅暴露于恶意元数据就足以损害代理的行为。

**减轻：**

*   **对不受信任的服务器要格外小心：** 重申：*不要连接到您不完全信任的 MCP 服务器。*元数据注入的风险使得这一点变得至关重要。

### 工作室传输安全

Stdio（标准输入/输出）传输通常用于与 CrewAI 应用程序在同一台计算机上运行的本地 MCP 服务器。

- **进程隔离**：虽然通常更安全，因为默认情况下不涉及网络暴露，但请确保 `StdioServerParameters` 运行的脚本或命令来自受信任的来源并具有适当的文件系统权限。恶意 Stdio 服务器脚本仍然可能损害您的本地系统。
- **输入清理**：如果您的 Stdio 服务器脚本采用源自代理交互的复杂输入，请确保脚本本身清理这些输入，以防止命令注入或脚本逻辑中的其他漏洞。
- **资源限制**：请注意，本地 Stdio 服务器进程会消耗本地资源（CPU、内存）。确保它表现良好并且不会耗尽系统资源。

### 混乱的副手攻击

[困惑的代理问题](https://en.wikipedia.org/wiki/Confused_deputy_problem) 是一个典型的安全漏洞，可能会在 MCP 集成中显现出来，特别是当 MCP 服务器充当使用 OAuth 2.0 进行授权的其他第三方服务（例如 Google Calendar、GitHub）的代理时。

**设想：**

1.  MCP 服务器（我们称之为`MCP-Proxy`）允许您的代理与`ThirdPartyAPI` 交互。
2.  `MCP-Proxy` 在与`ThirdPartyAPI` 的授权服务器通信时使用其自己的单一静态`client_id`。
3.  您作为用户，合法授权`MCP-Proxy`代表您访问`ThirdPartyAPI`。在此期间，`ThirdPartyAPI` 的身份验证服务器可能会在您的浏览器中设置一个 cookie，表明您同意 `MCP-Proxy` 的 `client_id`。
4.  攻击者制作恶意链接。此链接使用 `MCP-Proxy` 启动 OAuth 流程，但旨在欺骗 `ThirdPartyAPI` 的身份验证服务器。
5.  如果您点击此链接，`ThirdPartyAPI` 的身份验证服务器会看到您现有的 `MCP-Proxy` 的 `client_id` 的同意 cookie，它可能会*跳过*再次请求您的同意。
6.  然后，`MCP-Proxy` 可能会被诱骗将授权代码（针对 `ThirdPartyAPI`）转发给攻击者，或者攻击者可用来冒充您发送给 `MCP-Proxy` 的 MCP 授权代码。

**缓解措施（主要针对 MCP 服务器开发人员）：**

*   使用静态客户端 ID 进行下游服务的 MCP 代理服务器**必须**在与第三方服务启动 OAuth 流之前*获得连接到它们的*每个客户端应用程序或代理*的明确用户同意。这意味着 `MCP-Proxy` 本身应该显示同意屏幕。

**CrewAI 用户含义：**

*   如果 MCP 服务器重定向您进行多个 OAuth 身份验证，请务必小心，特别是如果它看起来出乎意料或请求的权限过于广泛。
*   更喜欢能够清楚地描述自己身份的 MCP 服务器，而不是它们可能代理的第三方服务。

### 远程传输安全（SSE 和可流式 HTTP）

通过服务器发送事件 (SSE) 或可流式 HTTP 连接到远程 MCP 服务器时，标准 Web 安全实践至关重要。

### 上交所安全考虑

### 一个。 DNS 重新绑定攻击（尤其是 SSE）

<Critical>
**防止 DNS 重新绑定攻击。**
</Critical>

DNS 重新绑定允许攻击者控制的网站绕过同源策略并向用户本地网络（例如`localhost`）或 Intranet 上的服务器发出请求。如果您在本地运行 MCP 服务器（例如，用于开发）并在类似浏览器的环境中运行代理（尽管对于典型的 CrewAI 后端设置不太常见）或者 MCP 服务器位于内部网络上，则这种风险特别大。

**MCP 服务器实施者的缓解策略：**
- **验证 `Origin` 和 `Host` 标头**：MCP 服务器（尤其是 SSE 服务器）应验证 `Origin` 和/或 `Host` HTTP 标头，以确保请求来自预期的域/客户端。
- **绑定到`localhost` (127.0.0.1)**：在本地运行MCP 服务器进行开发时，将它们绑定到`127.0.0.1` 而不是`0.0.0.0`。这可以防止网络上的其他计算机访问它们。
- **身份验证**：如果不用于公共匿名访问，则需要对 MCP 服务器的所有连接进行身份验证。

### b.使用 HTTPS

- **加密传输中的数据**：始终对远程 MCP 服务器的 URL 使用 HTTPS（HTTP 安全）。这会对 CrewAI 应用程序和 MCP 服务器之间的通信进行加密，从而防止窃听和中间人攻击。 `MCPServerAdapter` 将遵循 URL 中提供的方案（`http` 或 `https`）。

### c.令牌传递（反模式）

这主要是 MCP 服务器开发人员关心的问题，但了解它有助于选择安全服务器。

“令牌直通”是指 MCP 服务器接受来自 CrewAI 代理的访问令牌（这可能是*不同*服务的令牌，例如 `ServiceA`），并简单地将其传递到另一个下游 API (`ServiceB`)，而无需进行适当的验证。具体来说，`ServiceB`（或 MCP 服务器本身）应该只接受*为他们*显式颁发的令牌（即令牌中的“受众”声明与服务器/服务匹配）。

**风险：**

*   绕过 MCP 服务器或下游 API 上的安全控制（例如速率限制或细粒度权限）。
*   破坏审计追踪和问责制。
*   允许滥用被盗代币。

**缓解措施（针对 MCP 服务器开发人员）：**

*   MCP 服务器**不得**接受未明确为其颁发的令牌。他们必须验证令牌的受众声明。

**CrewAI 用户含义：**

*   虽然用户无法直接控制，但这凸显了连接到遵循安全最佳实践的精心设计的 MCP 服务器的重要性。

#### 认证与授权

- **验证身份**：如果 MCP 服务器提供敏感工具或对私有数据的访问，它必须实现强大的身份验证机制来验证客户端（您的 CrewAI 应用程序）的身份。这可能涉及 API 密钥、OAuth 令牌或其他标准方法。
- **最小权限原则**：确保`MCPServerAdapter` 使用的凭据（如果有）仅具有访问所需工具所需的权限。

### d.输入验证和清理

- **输入验证至关重要**：MCP 服务器**必须**严格验证从代理收到的所有输入*在*处理这些输入或将其传递给工具之前。这是针对许多常见漏洞的主要防御措施：
- **命令注入：** 如果工具根据输入构造 shell 命令、SQL 查询或其他解释语言语句，服务器必须仔细清理此输入，以防止恶意命令被注入和执行。
- **路径遍历：** 如果工具根据输入参数访问文件，服务器必须验证和清理这些路径，以防止访问未经授权的文件或目录（例如，通过阻止 `../` 序列）。
- **数据类型和范围检查：** 服务器必须确保输入数据符合预期的数据类型（例如字符串、数字、布尔值）并处于可接受的范围内或遵循定义的格式（例如 URL 的正则表达式）。
- **JSON 架构验证：** 所有工具参数都应根据其定义的 JSON 架构进行严格验证。这有助于及早捕获格式错误的请求。
- **客户端意识**：虽然服务器端验证至关重要，但作为 CrewAI 用户，请注意代理构造为发送到 MCP 工具的数据，特别是在与不太受信任的或新的 MCP 服务器交互时。

### e.速率限制和资源管理

- **防止滥用**：MCP 服务器应实施速率限制以防止滥用，无论是有意（拒绝服务攻击）还是无意（例如，配置错误的代理发出过多请求）。
- **客户端重试**：如果预计出现暂时性网络问题或服务器速率限制，请在 CrewAI 任务中实施合理的重试逻辑，但避免可能加剧服务器负载的激进重试。

## 4. 安全 MCP 服务器实施建议（针对开发人员）

如果您正在开发 CrewAI 代理可能连接到的 MCP 服务器，除了上述几点之外，还请考虑以下最佳实践：

- **遵循安全编码实践**：遵守您选择的语言和框架的标准安全编码原则（例如 OWASP Top 10）。
- **最小权限原则**：确保运行MCP服务器的进程（特别是`Stdio`）仅具有最低限度的必要权限。工具本身也应该以执行其功能所需的最低权限进行操作。
- **依赖项管理**：保持所有服务器端依赖项（包括操作系统包、语言运行时和第三方库）保持最新状态，以修补已知漏洞。使用工具扫描易受攻击的依赖项。
- **安全默认设置**：将您的服务器及其工具设计为默认安全。例如，可能有风险的功能应该默认关闭，或者需要明确选择加入并发出明确的警告。
- **工具的访问控制**：实施强大的机制来控制哪些经过身份验证和授权的代理或用户可以访问特定工具，尤其是那些功能强大、敏感或产生成本的工具。
- **安全错误处理**：服务器不应向客户端公开详细的内部错误消息、堆栈跟踪或调试信息，因为这些可能会揭示内部工作原理或潜在的漏洞。在服务器端全面记录错误以进行诊断。
- **全面的日志记录和监控**：实现安全相关事件的详细日志记录（例如身份验证尝试、工具调用、错误、授权更改）。监视这些日志是否存在可疑活动或滥用模式。
- **遵守MCP授权规范**：如果实施身份验证和授权，请严格遵循[MCP授权规范](https://modelcontextprotocol.io/specification/draft/basic/authorization)和相关[OAuth 2.0安全最佳实践](https://datatracker.ietf.org/doc/html/rfc9700)。
- **定期安全审核**：如果您的 MCP 服务器处理敏感数据、执行关键操作或公开暴露，请考虑由合格的专业人员进行定期安全审核。
