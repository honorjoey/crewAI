## Agent 概述

在 CrewAI 框架中，`Agent` 是一个自主单元，它可以：

- 执行特定的 task
- 根据自身的角色和目标做出决策
- 使用工具来达成目标
- 与其他 agent 沟通协作
- 保留交互记忆
- 在被允许时委派 task

<Tip>
  可以把 agent 看作具有特定技能、专长和职责的专业团队成员。例如，
  `Researcher` agent 可能擅长收集和分析信息，而 `Writer` agent
  可能更擅长创作内容。
</Tip>

<Note type="info" title="企业版增强：可视化 Agent 构建器">
CrewAI AMP 包含可视化 Agent 构建器，无需编写代码即可简化 agent 的创建与配置。以可视化方式设计 agent 并进行实时测试。

![Visual Agent Builder Screenshot](/images/enterprise/crew-studio-interface.png)

可视化 Agent 构建器支持：

- 基于表单界面的直观 agent 配置
- 实时测试与验证
- 包含预配置 agent 类型的模板库
- 轻松自定义 agent 属性与行为
</Note>

## 创建 Agent

在 CrewAI 中创建 agent 有两种常见方式：使用**JSONC 项目配置（推荐）**或**直接在代码中定义**。

### JSONC 配置（推荐）

使用 `crewai create crew <name>` 创建的新项目采用 JSON 优先的配置方式。每个 agent 在 `agents/<agent_name>.jsonc` 中定义，`crew.jsonc` 列出哪些 agent 属于该 crew。

按照[安装](/zh-CN/installation)章节的说明创建 CrewAI 项目后，编辑 `agents/` 目录下生成的文件。

<Note>
在 `role`、`goal` 或 `backstory` 中使用 `{placeholder}` 占位符。将默认值放在 `crew.jsonc` 的 `inputs` 下；`crewai run` 会提示输入任何缺失的值。
</Note>

下面是一个 `agents/researcher.jsonc` 文件示例：

```jsonc agents/researcher.jsonc
{
  "role": "{topic} Senior Data Researcher",
  "goal": "Uncover cutting-edge developments in {topic}",
  "backstory": "You find the most relevant information and present it clearly.",
  "llm": "openai/gpt-4o",
  "tools": ["SerperDevTool"],
  "settings": {
    "verbose": true,
    "allow_delegation": false,
    "max_iter": 20
  }
}
```

然后在 `crew.jsonc` 中引入该 agent：

```jsonc crew.jsonc
{
  "name": "Research Crew",
  "agents": ["researcher"],
  "tasks": [
    {
      "name": "research_task",
      "description": "Research {topic}",
      "expected_output": "A concise briefing about {topic}",
      "agent": "researcher"
    }
  ],
  "inputs": {
    "topic": "AI Agents"
  }
}
```

Agent 文件支持任何公开的 `Agent` 字段。常用字段包括 `role`、`goal`、`backstory`、`llm`、`tools`、`function_calling_llm`、`guardrail`、`step_callback` 和 `settings`。诸如 `verbose`、`allow_delegation`、`max_iter`、`max_rpm`、`memory`、`cache`、`planning_config` 和 `use_system_prompt` 等行为选项可以放在顶层或 `settings` 下；`settings` 中的值优先。

<Note>
  JSONC 支持注释和尾随逗号。如果 `agents/<name>.jsonc` 和 `agents/<name>.json` 同时存在，CrewAI 会使用 JSONC 文件。
</Note>

### 经典 YAML 配置

使用 `crewai create crew <name> --classic` 创建的经典项目使用 `config/agents.yaml` 和 `crew.py` 中的 `@CrewBase` 类。对于希望使用 Python 装饰器或已有 YAML 项目的团队，这种方式仍然受支持。

### 直接在代码中定义

你可以通过实例化 `Agent` 类直接在代码中创建 agent。下面是一个展示所有可用参数的完整示例：

```python Code
from crewai import Agent
from crewai_tools import SerperDevTool

# Create an agent with all available parameters
agent = Agent(
    role="Senior Data Scientist",
    goal="Analyze and interpret complex datasets to provide actionable insights",
    backstory="With over 10 years of experience in data science and machine learning, "
              "you excel at finding patterns in complex datasets.",
    llm="gpt-4",  # Default: OPENAI_MODEL_NAME or "gpt-4"
    function_calling_llm=None,  # Optional: Separate LLM for tool calling
    verbose=False,  # Default: False
    allow_delegation=False,  # Default: False
    max_iter=20,  # Default: 20 iterations
    max_rpm=None,  # Optional: Rate limit for API calls
    max_execution_time=None,  # Optional: Maximum execution time in seconds
    max_retry_limit=2,  # Default: 2 retries on error
    allow_code_execution=False,  # Default: False
    code_execution_mode="safe",  # Default: "safe" (options: "safe", "unsafe")
    respect_context_window=True,  # Default: True
    use_system_prompt=True,  # Default: True
    multimodal=False,  # Default: False
    inject_date=False,  # Default: False
    date_format="%Y-%m-%d",  # Default: ISO format
    reasoning=False,  # Default: False
    max_reasoning_attempts=None,  # Default: None
    tools=[SerperDevTool()],  # Optional: List of tools
    knowledge_sources=None,  # Optional: List of knowledge sources
    embedder=None,  # Optional: Custom embedder configuration
    system_template=None,  # Optional: Custom system prompt template
    prompt_template=None,  # Optional: Custom prompt template
    response_template=None,  # Optional: Custom response template
    step_callback=None,  # Optional: Callback function for monitoring
)
```

### 参数详解

#### 关键参数

- `role`、`goal` 和 `backstory` 是必需的，决定了 agent 的行为
- `llm` 决定使用的语言模型（默认：OpenAI 的 GPT-4）

#### 记忆与上下文

- `memory`：启用后可保留对话历史
- `respect_context_window`：防止 token 限制问题
- `knowledge_sources`：添加特定领域的知识库

#### 执行控制

- `max_iter`：给出最佳答案前的最大尝试次数
- `max_execution_time`：超时时间（秒）
- `max_rpm`：API 调用的速率限制
- `max_retry_limit`：出错时的重试次数

#### 代码执行

<Warning>
  `allow_code_execution` 和 `code_execution_mode` 已被弃用。`CodeInterpreterTool` 已从 `crewai-tools` 中移除。请使用专用的沙箱服务（如 [E2B](https://e2b.dev) 或 [Modal](https://modal.com)）来安全地执行代码。
</Warning>

- `allow_code_execution` _（已弃用）_：之前用于通过 `CodeInterpreterTool` 启用内置代码执行。
- `code_execution_mode` _（已弃用）_：之前用于控制执行模式（`"safe"` 使用 Docker，`"unsafe"` 直接执行）。

#### 高级特性

- `multimodal`：启用多模态能力以处理文本与视觉内容
- `reasoning`：让 agent 在执行 task 前先反思并制定计划
- `inject_date`：自动将当前日期注入 agent 的提示词

#### 模板

- `system_template`：定义 agent 的核心行为
- `prompt_template`：组织输入格式
- `response_template`：格式化 agent 的响应

<Note>
  使用自定义模板时，请确保同时定义 `system_template` 和
  `prompt_template`。`response_template` 是可选的，但建议定义以保证
  输出格式的一致性。
</Note>

<Note>
  使用自定义模板时，可以在模板中使用 `{role}`、`{goal}` 和
  `{backstory}` 等变量。这些变量会在执行时自动填充。
</Note>

## Agent 工具

可以为 agent 配备各种工具来增强其能力。CrewAI 支持来自以下来源的工具：

- [CrewAI Toolkit](https://github.com/joaomdmoura/crewai-tools)
- [LangChain Tools](https://python.langchain.com/docs/integrations/tools)

为 agent 添加工具的方式如下：

```python Code
from crewai import Agent
from crewai_tools import SerperDevTool, WikipediaTools

# Create tools
search_tool = SerperDevTool()
wiki_tool = WikipediaTools()

# Add tools to agent
researcher = Agent(
    role="AI Technology Researcher",
    goal="Research the latest AI developments",
    tools=[search_tool, wiki_tool],
    verbose=True
)
```

## Agent 记忆与上下文

Agent 可以保留交互记忆，并使用来自之前 task 的上下文。这对于需要跨多个 task 保留信息的复杂工作流特别有用。

```python Code
from crewai import Agent

analyst = Agent(
    role="Data Analyst",
    goal="Analyze and remember complex data patterns",
    memory=True,  # Enable memory
    verbose=True
)
```

<Note>
  启用 `memory` 后，agent 会在多次交互之间保持上下文，从而提升其
  处理复杂、多步骤 task 的能力。
</Note>

## 上下文窗口管理

CrewAI 内置了完善的自动上下文窗口管理机制，用于处理对话超出语言模型 token 限制的情况。这一强大特性由 `respect_context_window` 参数控制。

### 上下文窗口管理的工作原理

当 agent 的对话历史超出 LLM 的上下文窗口时，CrewAI 会自动检测到这种情况，并可以选择：

1. **自动摘要内容**（当 `respect_context_window=True` 时）
2. **以错误终止执行**（当 `respect_context_window=False` 时）

### 自动上下文处理（`respect_context_window=True`）

这是大多数场景下的**默认且推荐的设置**。启用后，CrewAI 将：

```python Code
# Agent with automatic context management (default)
smart_agent = Agent(
    role="Research Analyst",
    goal="Analyze large documents and datasets",
    backstory="Expert at processing extensive information",
    respect_context_window=True,  # 🔑 Default: auto-handle context limits
    verbose=True
)
```**超出上下文限制时会发生什么：**- ⚠️**警告信息**：`"Context length exceeded. Summarizing content to fit the model context window."`
- 🔄**自动摘要**：CrewAI 智能地对对话历史进行摘要
- ✅**继续执行**：task 基于摘要后的上下文无缝继续执行
- 📝**信息保留**：在减少 token 数量的同时保留关键信息

### 严格上下文限制（`respect_context_window=False`）

当你需要精确控制，并且宁愿停止执行也不愿丢失任何信息时：

```python Code
# Agent with strict context limits
strict_agent = Agent(
    role="Legal Document Reviewer",
    goal="Provide precise legal analysis without information loss",
    backstory="Legal expert requiring complete context for accurate analysis",
    respect_context_window=False,  # ❌ Stop execution on context limit
    verbose=True
)
```**超出上下文限制时会发生什么：**- ❌**错误信息**：`"Context length exceeded. Consider using smaller text or RAG tools from crewai_tools."`
- 🛑**执行停止**：task 执行立即中止
- 🔧**需要人工干预**：你需要调整处理方案

### 选择合适的设置

#### 在以下情况使用 `respect_context_window=True`（默认）：

- **处理大型文档**，可能超出上下文限制
- **长时间对话**，可以接受一定程度的摘要
- **研究类 task**，整体上下文比精确细节更重要
- **原型开发阶段**，希望执行过程更健壮

```python Code
# Perfect for document processing
document_processor = Agent(
    role="Document Analyst",
    goal="Extract insights from large research papers",
    backstory="Expert at analyzing extensive documentation",
    respect_context_window=True,  # Handle large documents gracefully
    max_iter=50,  # Allow more iterations for complex analysis
    verbose=True
)
```

#### 在以下情况使用 `respect_context_window=False`：

- **精确性至关重要**，不能接受信息丢失
- **法律或医疗类 task**，需要完整上下文
- **代码审查**，遗漏细节可能引入 bug
- **金融分析**，准确性是重中之重

```python Code
# Perfect for precision tasks
precision_agent = Agent(
    role="Code Security Auditor",
    goal="Identify security vulnerabilities in code",
    backstory="Security expert requiring complete code context",
    respect_context_window=False,  # Prefer failure over incomplete analysis
    max_retry_limit=1,  # Fail fast on context issues
    verbose=True
)
```

### 处理大规模数据的替代方案

处理非常大的数据集时，可以考虑以下策略：

#### 1. 使用 RAG 工具

```python Code
from crewai_tools import RagTool

# Create RAG tool for large document processing
rag_tool = RagTool()

rag_agent = Agent(
    role="Research Assistant",
    goal="Query large knowledge bases efficiently",
    backstory="Expert at using RAG tools for information retrieval",
    tools=[rag_tool],  # Use RAG instead of large context windows
    respect_context_window=True,
    verbose=True
)
```

#### 2. 使用知识源

```python Code
# Use knowledge sources instead of large prompts
knowledge_agent = Agent(
    role="Knowledge Expert",
    goal="Answer questions using curated knowledge",
    backstory="Expert at leveraging structured knowledge sources",
    knowledge_sources=[your_knowledge_sources],  # Pre-processed knowledge
    respect_context_window=True,
    verbose=True
)
```

### 上下文窗口最佳实践

1. **监控上下文使用情况**：启用 `verbose=True` 以观察上下文管理的运作
2. **追求高效设计**：合理组织 task 以尽量减少上下文累积
3. **使用合适的模型**：选择上下文窗口大小适配你 task 的 LLM
4. **两种设置都测试**：分别尝试 `True` 和 `False`，看哪种更适合你的场景
5. **与 RAG 结合**：对于超大数据集，使用 RAG 工具而不要只依赖上下文窗口

### 上下文问题排查**如果你遇到上下文限制错误：**```python Code
# Quick fix: Enable automatic handling
agent.respect_context_window = True

# Better solution: Use RAG tools for large data
from crewai_tools import RagTool
agent.tools = [RagTool()]

# Alternative: Break tasks into smaller pieces
# Or use knowledge sources instead of large prompts
```**如果自动摘要丢失了重要信息：**```python Code
# Disable auto-summarization and use RAG instead
agent = Agent(
    role="Detailed Analyst",
    goal="Maintain complete information accuracy",
    backstory="Expert requiring full context",
    respect_context_window=False,  # No summarization
    tools=[RagTool()],  # Use RAG for large data
    verbose=True
)
```

<Note>
  上下文窗口管理是自动且透明进行的。你无需调用任何特殊函数——只需将
  `respect_context_window` 设置为你偏好的行为，其余交给 CrewAI
  处理即可！
</Note>

## 使用 `kickoff()` 直接与 Agent 交互

通过 `kickoff()` 方法，可以在不经过 task 或 crew 工作流的情况下直接使用 agent。当你不需要完整的 crew 编排能力时，这提供了一种更简单的 agent 交互方式。

### `kickoff()` 的工作原理

`kickoff()` 方法允许你直接向 agent 发送消息并获得响应，类似于与 LLM 交互，但具备 agent 的全部能力（工具、推理等）。

```python Code
from crewai import Agent
from crewai_tools import SerperDevTool

# Create an agent
researcher = Agent(
    role="AI Technology Researcher",
    goal="Research the latest AI developments",
    tools=[SerperDevTool()],
    verbose=True
)

# Use kickoff() to interact directly with the agent
result = researcher.kickoff("What are the latest developments in language models?")

# Access the raw response
print(result.raw)
```

### 参数与返回值

| 参数         | 类型                               | 说明                                                               |
| :---------------- | :--------------------------------- | :------------------------------------------------------------------------ |
| `messages`        | `Union[str, List[Dict[str, str]]]` | 字符串形式的查询，或包含 role/content 的消息字典列表 |
| `response_format` | `Optional[Type[Any]]`              | 可选的 Pydantic 模型，用于结构化输出                             |

该方法返回一个 `LiteAgentOutput` 对象，包含以下属性：

- `raw`：包含原始输出文本的字符串
- `pydantic`：解析后的 Pydantic 模型（当提供了 `response_format` 时）
- `agent_role`：产生该输出的 agent 的角色
- `usage_metrics`：本次执行的 token 使用指标

### 结构化输出

将 Pydantic 模型作为 `response_format` 传入即可获得结构化输出：

```python Code
from pydantic import BaseModel
from typing import List

class ResearchFindings(BaseModel):
    main_points: List[str]
    key_technologies: List[str]
    future_predictions: str

# Get structured output
result = researcher.kickoff(
    "Summarize the latest developments in AI for 2025",
    response_format=ResearchFindings
)

# Access structured data
print(result.pydantic.main_points)
print(result.pydantic.future_predictions)
```

### 多条消息

你也可以以消息字典列表的形式提供对话历史：

```python Code
messages = [
    {"role": "user", "content": "I need information about large language models"},
    {"role": "assistant", "content": "I'd be happy to help with that! What specifically would you like to know?"},
    {"role": "user", "content": "What are the latest developments in 2025?"}
]

result = researcher.kickoff(messages)
```

最后一条 `user` 消息是 agent 要回答的请求。其他每条消息都会保留其
角色及其相对该请求的位置，因此即使对话以 assistant 或 tool 消息结尾，
agent 仍会回答用户的问题，并在其后保留这些末尾消息。如果完全没有
`user` 消息，则最后一条消息会被视为请求。

### 异步支持

`kickoff_async()` 提供了参数相同的异步版本：

```python Code
import asyncio

async def main():
    result = await researcher.kickoff_async("What are the latest developments in AI?")
    print(result.raw)

asyncio.run(main())
```

<Note>
  `kickoff()` 方法使用与 crew 中 agent 相同的 `AgentExecutor` 来运行
  agent，只是不涉及 task 或 crew，并保留 agent 的全部配置（角色、
  目标、背景故事、工具等）。
</Note>

## 对话式 Agent（实验性）

启用 `conversational=True` 可以为直接使用的 Agent 提供一个对话式 Flow 会话。`handle_turn()` 会在每一轮将会话中的用户/助手历史传给所配置的 Agent 和工具，并返回常规的 Agent 输出。

<Warning>
该 API 为实验性功能，需要匹配的 SDK 构建版本。其契约在正式发布前可能发生变化。
</Warning>

```python
from crewai import Agent, LLM

agent = Agent(
    role="Assistant",
    goal="Help the user accurately.",
    backstory="A general-purpose assistant.",
    llm=LLM(model="openai/gpt-6.1-sol", api="responses"),
    conversational=True,
)

agent.handle_turn("Remember that my project is Cedar Finch.")
reply = agent.handle_turn("What is my project's name?")
print(reply.raw)
```

对于交互式对话，使用与对话式 Flow 相同的 `chat()` 约定：

```python
agent.chat()          # Plain terminal REPL
agent.chat(tui=True)  # Full terminal UI
```

`tui=True` 需要交互式终端和匹配的 CLI 构建版本。两种模式都接受 `session_id`、`exit_commands` 以及转发给 `handle_turn()` 的选项。自定义提示符、输入/输出可调用对象和 `skip_empty` 是仅 REPL 可用的选项。开始聊天前无需创建或传入 Flow。

普通 REPL 和 TUI 都会自动流式输出响应；你不需要 `LLM(stream=True)`。可以通过 `agent.chat(stream=False)`（`tui=True` 时同样支持）或显式的 `LLM(stream=False)` 禁用 token 流式输出。聊天中显式设置的 `stream=True` 会覆盖 LLM 的设置。流式输出的作用范围仅限每一轮对话，不会改变 LLM 配置或独立 `kickoff()` 的行为。自定义 `output_fn` 每轮会收到一个完整的响应；如需自定义流式传输，请使用 `stream_turn()`。

一个 Agent 只复用于一个对话。第一轮会绑定其会话 ID；切换到其他 ID 会在历史到达模型之前抛出 `ValueError`。在该 Agent 上重叠执行多轮会抛出 `RuntimeError`，包括 REPL、TUI 和托管 Flow 桥接所使用的流式轮次。为每个独立对话创建单独的 Agent。Python 和 Pydantic 方式的 Agent 副本都会以全新的历史和会话保护开始，即使是在活动轮次中复制的也是如此。如需高级持久化配置，`agent.as_flow()` 会暴露底层会话。历史默认保存在内存中；进程级恢复需要显式的 Flow 持久化。会话 ID 用于标识状态；应用程序仍须自行对持久化会话的访问进行授权。

普通 Agent 默认 `conversational=False`。即使启用了对话功能，直接调用 `kickoff()` 和 `kickoff_async()` 仍是相互独立的执行；要保留会话历史请使用 `handle_turn()`。现有的 Crew/Task 执行保持当前行为不变。

## 从早期版本升级 Agent

1.15.29 版本移除了 `CrewAgentExecutor`，并改变了每个 agent 处理大型工具结果、长对话和重复工具调用的方式。这些变化适用于 crew 中的 agent、Flow 中的 agent 以及通过 `kickoff()` 调用的 agent。例外是启用了[规划](/zh-CN/concepts/planning)的 agent 的计划步骤：其工具结果不会被转存，其对话不会被摘要，且重复调用计数会在每个步骤重新开始。如果你正从 1.15.28 或更早版本迁移，请逐项检查以下内容。

### `CrewAgentExecutor` 已被移除

`AgentExecutor` 是唯一的 agent 执行器。它自 1.14.5 起就是默认执行器，因此从未设置过 `executor_class` 的 agent 本来就运行在它之上。

- `executor_class=CrewAgentExecutor`，或配置文件中的字符串 `"CrewAgentExecutor"`，会以 `CrewAgentExecutor has been removed. Use crewai.agents.agent_executor.AgentExecutor.` 校验失败。请移除该设置。
- 以下导入路径已不存在：`crewai.agents.crew_agent_executor`、`crewai.agents.CrewAgentExecutor`、`crewai.experimental.agent_executor` 模块、`crewai.experimental.AgentExecutor` 和 `crewai.experimental.CrewAgentExecutorFlow`。请从 `crewai.agents` 导入执行器：

```python Code
from crewai.agents import AgentExecutor
```

没有任何设置可以恢复旧的执行器。

### 超大工具结果会被转存

当原生工具调用返回的结果超过模型上下文窗口的 25% 时，agent 不再接收完整结果，而是收到一段简短预览和一个指向临时文件的引用，并通过 `Read a deferred tool result` 工具（模型看到的名称是 `read_a_deferred_tool_result`）分段读取其余内容，CrewAI 会在需要时将该工具添加给 agent。

- 失败的工具调用、设置了 `result_as_answer=True` 的工具以及基于文本（ReAct）的工具调用永远不会被转存。
- 该文件位于系统临时目录下的私有目录中。只有产生它的那次运行可以读取它，并且在对应的 task 或 `kickoff()` 调用结束时会被删除。

若要在对话中保留完整的工具结果，可为该 agent 关闭转存功能：

```python Code
from crewai import Agent

agent = Agent(
    role="Source Reviewer",
    goal="Quote sources exactly",
    backstory="Checks every quote against the original text",
    use_better_compaction=False,  # Keep whole tool results in the conversation
)
```

### 上下文会在溢出前被摘要

当 `respect_context_window=True`（默认值）时，agent 现在会在发送前测量每个请求的大小。当请求超过模型的上下文窗口时，CrewAI 会先对较早的对话进行摘要，而不是等待提供商拒绝请求。摘要可能丢失诸如精确引文之类的细节。

设置 `respect_context_window=False` 可关闭摘要功能。此时过长的请求会以 `SystemExit("Context length exceeded and user opted not to summarize...")` 终止运行。`SystemExit` 不是 `Exception` 的子类，因此 `except Exception` 块无法捕获它。

### 重复的工具调用会终止 Task

当 agent 在一次运行中用相同的参数调用同一个工具并五次获得相同结果时，CrewAI 会以 `ToolExecutionFailedError` 终止该 task，并给出 agent `called '<tool>' with the same arguments 5 times and got the same result each time` 的消息。

- 该计数覆盖整个 task 或 `kickoff()` 调用，而不仅仅是连续调用，并且包含由工具缓存返回的结果。
- 无论 `tool_failure_policy` 设置为何，这一终止都会发生，且 `max_retry_limit` 不会对其重试。
- 五次的限制是固定的。没有任何设置可以修改或禁用它。

### 上下文窗口大小是如何确定的

转存和摘要的衡量基准都是 CrewAI 为该模型使用的上下文窗口：其内置 LiteLLM 模型目录中所列窗口的 85%。目录中不存在的模型会回退到提供商默认值。对于 OpenAI、Azure、Bedrock、OpenAI 兼容（如 OpenRouter）以及经 LiteLLM 路由的模型，该默认值为 8,192 个 token，因此经过 85% 比例后 CrewAI 使用 6,963，两个功能都会远早于模型真实窗口允许的时机就被触发。未重写 `get_context_window_size()` 的自定义 `BaseLLM` 子类使用 4,096。要查看 CrewAI 实际使用的大小，可在 LLM 上调用 `get_context_window_size()`。LLM 会按运行时的方式构建，因此必须设置提供商的 API 密钥：

```python Code
from crewai import LLM

llm = LLM(model="openrouter/your-provider/your-model")
print(llm.get_context_window_size())
```

## 重要注意事项与最佳实践

### 安全与代码执行

<Warning>
  `allow_code_execution` 和 `code_execution_mode` 已被弃用，`CodeInterpreterTool` 已被移除。请使用专用的沙箱服务（如 [E2B](https://e2b.dev) 或 [Modal](https://modal.com)）来安全地执行代码。
</Warning>

### 性能优化

- 使用 `respect_context_window: true` 防止 token 限制问题
- 设置合适的 `max_rpm` 以避免速率限制
- 启用 `cache: true` 以提升重复性 task 的性能
- 根据 task 复杂度调整 `max_iter` 和 `max_retry_limit`

### 记忆与上下文管理

- 利用 `knowledge_sources` 提供特定领域的信息
- 使用自定义嵌入模型时配置 `embedder`
- 使用自定义模板（`system_template`、`prompt_template`、`response_template`）对 agent 行为进行精细控制

### 高级特性

- 对需要在执行复杂 task 前进行规划和反思的 agent 启用 `reasoning: true`
- 设置合适的 `max_reasoning_attempts` 来控制规划迭代次数（None 表示不限次数）
- 使用 `inject_date: true` 为处理时间敏感 task 的 agent 提供当前日期感知
- 使用标准 Python datetime 格式代码通过 `date_format` 自定义日期格式
- 对需要同时处理文本和视觉内容的 agent 启用 `multimodal: true`

### Agent 协作

- 当 agent 需要协同工作时启用 `allow_delegation: true`
- 使用 `step_callback` 监控并记录 agent 的交互
- 考虑为不同用途使用不同的 LLM：
  - 主 `llm` 用于复杂推理
  - `function_calling_llm` 用于高效的工具调用

### 日期感知与推理

- 使用 `inject_date: true` 为处理时间敏感 task 的 agent 提供当前日期感知
- 使用标准 Python datetime 格式代码通过 `date_format` 自定义日期格式
- 有效的格式代码包括：%Y（年）、%m（月）、%d（日）、%B（月份全称）等
- 无效的日期格式会以警告形式记录，并且不会修改 task 描述
- 对能从前期规划和反思中获益的复杂 task 启用 `reasoning: true`

### 模型兼容性

- 对不支持系统消息的旧模型设置 `use_system_prompt: false`
- 确保所选的 `llm` 支持你需要的功能（例如函数调用）

## 常见问题排查

1. **速率限制**：如果你遇到 API 速率限制：

   - 设置合适的 `max_rpm`
   - 对重复性操作使用缓存
   - 考虑批量处理请求

2. **上下文窗口错误**：如果你超出了上下文限制：

   - 启用 `respect_context_window`
   - 使用更高效的提示词
   - 定期清理 agent 记忆

3. **代码执行问题**：如果代码执行失败：

   - 确认已安装 Docker 以使用安全模式
   - 检查执行权限
   - 检查代码沙箱设置

4. **记忆问题**：如果 agent 的响应看起来不一致：
   - 检查知识源配置
   - 检查对话历史管理

请记住，只有根据具体使用场景进行配置，agent 才能发挥最大效用。请花时间理解你的需求，并据此调整这些参数。
